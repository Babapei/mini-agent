# Mini Agent 设计说明

本文在写业务代码之前冻结设计。实现与本文冲突时，先改文档并记下原因，再改代码。

## Agent Loop 如何设计

主循环在 `mini_agent/agent/loop.py`。每一轮只做四件事：把当前 Context 交给 LLM，记录决策，执行决策里的工具或结束，把工具结果追加回 Context。

```text
User Task
  -> 组装 Context（系统提示、用户任务、历史决策、工具结果）
  -> 超过总长度时，压缩更早的工具结果，保留最近一条全文
  -> LLM 产出 Decision
  -> 第一次工具调用前，若决策带了计划，先写入 Plan
  -> 上一轮工具失败且决策带了修订时，写入 Plan Update
  -> Decision 含工具调用：先查权限，再逐个执行，结果写回 Context，进入下一轮
  -> Decision 只有最终答案：结束
  -> 轮数耗尽或连续相同失败：结束并说明原因
```

Agent 不读取业务文件，也不计算销售额。它只执行 LLM 点名的工具。

`Decision` 的行动仍然只有一类：工具调用，或一份最终答案。可选的 `plan` 和 `plan_update` 只是附在同一次决策上的文字，不能代替工具调用。循环自己还会在轮数耗尽、连续失败或模型响应不可用时写出停止说明。

一轮里如果同时出现工具调用和最终答案，循环只执行工具调用。最终答案必须出现在没有工具调用的那一轮。

## Tool 如何定义

每个工具有名称、描述、JSON Schema 参数和执行函数。注册表按名称查找。调用前检查必填项、参数类型和未知字段。校验失败返回失败结果，不抛给循环外。

每个工具声明一种权限：`read`、`write` 或 `compute`。调用前检查本次运行是否允许。默认三种都允许。不允许时返回 `权限不足：<工具名> 需要 <权限>`，不执行工具。命令行用 `--allow` 限制，例如 `--allow read`。

| 工具 | 权限 | 必填参数 | 行为 |
| --- | --- | --- | --- |
| `read_file` | `read` | `path` | 读取 workspace 内的文本文件 |
| `write_file` | `write` | `path`、`content` | 写入 workspace 内的文本文件，必要时创建父目录 |
| `search_text` | `read` | `query`，可选 `path` | 按字面量搜索，返回 `文件:行号:内容` |
| `calculator` | `compute` | `expression` | 只计算数字、括号和 `+ - * / // % **` |
| `tool_search` | `read` | `query` | 在工具名和说明里查找。空查询失败。找不到时返回空文本 |
| `delegate` | `read` | `task` | 把一句子任务交给下一层。默认不注册 |

`delegate` 只在命令行加上 `--sub-agent` 时注册。子循环使用同一套 workspace 和工具，不能再委托，默认最多 6 轮。子 Trace 写到本次 Trace 目录的 `sub/`。子循环失败时，父循环收到失败结果。

路径先按 workspace 根目录解析，再确认真实路径仍在根目录之内。`../`、绝对路径和指向外部的符号链接都拒绝。

`calculator` 用语法树解释表达式，不调用 `eval` 或 `exec`。指数绝对值大于 20 时拒绝，避免过大的计算。

## 如何判断任务结束

循环只在下面三种情况结束：

1. LLM 给出最终答案，且该轮没有工具调用。
2. 已执行的决策轮数达到上限。默认 12，可由调用方配置。
3. 判定无法继续。触发条件是：模型没有给出工具调用或最终答案；模型响应无法解析；同一个工具和同一组参数连续失败达到 2 次。

任务结束时仍输出一份最终文本。无法完成时，文本写明停止原因和最后一次工具错误，不把未完成说成已完成。

## 如何避免无限调用

三道限制同时生效：

- 决策轮数上限。达到上限后不再请求 LLM。
- 相同失败签名最多连续出现 2 次。签名是工具名加上排序后的参数 JSON。第二次失败后立即停止，不再把同一次失败交回模型重试。
- Mock 对每个已知任务有固定的工具步数。超出计划时直接给出无法继续，不另发明新的工具调用。

成功调用或换了一组参数会清零连续失败计数。因此「先失败、再改参数」可以继续，「同一错误反复重试」不会继续。

## Tool 执行失败如何处理

工具内部的预期错误和未预期异常都变成同一种结果：`ok=false` 和错误文本。循环不因工具失败而崩溃。

处理顺序：

1. 权限不足、参数不合法、路径越界、文件不存在、表达式非法，都返回失败结果。权限检查在执行之前，和路径沙箱是两道不同的失败。
2. 失败结果写入 Context 和 Trace，下一轮由 LLM 决定是改参数、换工具，还是结束。
3. `read_file` 返回「文件不存在」时，等这一轮的工具结果都记完，再追加一条恢复提示：可以用 `search_text` 按文件名查找，不要用同一路径再读。提示不插在同一次回复的工具结果中间。程序不代替模型发出搜索。路径越界不追加这句提示。
4. 若下一轮又用同一签名失败，循环停止，并在最终答案中写明工具名、参数和错误。
5. HTTP 层的超时、连接错误和 5xx 只在模型适配器内重试，最多再试 2 次。4xx 不重试。工具业务失败不走 HTTP 重试。线上请求仍是一次返回。流式分片只在录好的响应上解析，参数 JSON 未收齐时不产生工具调用。

恢复任务使用这条路径：先读不存在的 `data/missing.txt`，模型看到失败后再搜索 FIXME 并计算销售额。

## Agent、LLM、Tool、Context 如何划分职责

- Agent：轮数、终止、失败政策和 Trace。不理解 CSV，不汇总 TODO。
- LLM：只看消息和 Tool Schema，产出 `Decision`。不执行工具，不碰文件系统。Mock 和 OpenAI 兼容接口实现同一个 `decide(messages, tools)`。
- Tool：校验参数，做一件事，返回成功输出或失败错误。不决定下一步。
- Context：系统提示、用户任务、助手决策、工具结果、步数和 workspace 根目录。单条工具输出默认最多保留 8000 个字符，超出的部分截断并注明。全部消息超过 24000 字时，除最近一条工具结果外，更早的工具结果收成一行，只保留工具名、成败和首行。压缩不调用模型。

Mock 可以按用户原文里的关键词选择第一步，这是模型决策的替身，不是 Agent 循环里的分支。它随后的每一步必须读取工具结果。报告中的合计数字只允许抄计算器的返回值。

## 当前实现最大的限制是什么

Mock 不是通用规划器。它只认识计划书里固定的任务句式：汇总 TODO、计算销售额、缺失文件后的恢复、越界或非法算式。其他说法会直接回答无法规划，不会假装调用了工具。

真实模型依赖调用方提供 OpenAI 兼容接口的密钥、地址和模型名。没有这些变量时，适配器代码和夹具测试仍然有效，但不能产生真实模型 Trace。

拓展阶段已经落地的有：工具权限、调用前的计划、失败后的计划修订、上下文压缩、命令行边跑边打印、文件不存在时的恢复提示、`tool_search`，以及默认关闭的一层子代理。线上真实模型请求仍是一次返回的 HTTP，流式分片只在录好的响应上测试。单条工具输出超过 8000 字仍会截断，长搜索结果可能丢掉后半部分。多轮对话仍然不做。

## 消息与 Trace

`Message.role` 取 `system`、`user`、`assistant`、`tool`。工具消息带工具名、`ok` 和文本。

Trace 同时写 `trace.md` 和 `trace.jsonl`。Markdown 用二级标题按实际发生的顺序记录。一次完整调用里常见的是 `User`、`Plan`、`Agent Decision`、`Tool Call`、`Tool Result`，最后是 `Final Answer`。下面几节只在对应情况出现：

- `Plan`：第一次工具调用之前，决策里带了计划。
- `Plan Update`：上一轮工具失败，并且这次决策带了修订。Mock 会写。真实模型的适配器不从回复里提取修订，所以 DeepSeek 的 Trace 里没有这一节。
- `Recovery Hint`：`read_file` 报告文件不存在。
- `Context Compression`：全部消息超过 24000 字，写明压缩了几条。未超过时不出现。
